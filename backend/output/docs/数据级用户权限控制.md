# 数据级用户权限控制 — 改造目标与任务领单

> **状态：📌 已规划，暂缓实施**（有更优先需求，先记录目标与方案，待排期）
> **范围：仅 autotest 模块**
> **方案：方案 A（集中式归属守卫 `ensure_owner_or_superuser`）**

---

## 一、改造目标

为 autotest 模块的数据修改/删除操作增加**数据级归属校验**，实现规则：

> **只有超级用户（`is_superuser`）可以修改/删除其他人创建的数据；非超级用户只能修改/删除自己创建（`created_user == 当前用户`）的数据。**

## 二、背景与现状（审查结论）

### 现有权限模型
- 用户模型有 `is_superuser` 字段（超级用户/管理员）。
- 数据模型经 `MaintainMixin` 有 `created_user` 字段（创建人，大写用户名，长度 16）。
- 当前用户经 `backend/services/ctx.py` 的 `get_current_username()` 获取（返回大写、截断 16 位）。
- 鉴权依赖在 `backend/services/dependency.py`：
  - `AuthControl.is_authed`：认证（JWT），返回 User 对象，设置 `CTX_USER_ID`/`CTX_USERNAME`。
  - `PermissionControl.has_permission`：**路由级**权限，校验角色是否拥有该 `(method, path)`，超级用户绕过。

### 核心缺口（已核验）
- 全代码库 `created_user ==`/`created_user !=` 归属比较 **0 命中**。
- `is_superuser` 仅用于：路由级放行（`dependency.py:53`）、保护超级用户不被重置密码（`user_crud.py:226`）。
- **基类 `ScaffoldCrud` 的 `update`/`soft_delete`/`hard_delete`/`batch_update` 等方法均不做归属校验**，只按 id 操作。
- 结论：**唯一防线是路由级权限**。一旦某普通用户的角色被授予某 update/delete 接口，即可改/删**任何人**的记录，不受 `created_user` 约束 → **真实越权风险**。

### 审查清单（18 个 crud 文件）
| 分类 | 文件 |
|------|------|
| 🔴 未校验归属（含 created_user，需接入，共 16 个） | router_crud、role_crud、menu_crud、autotest_tag_crud、autotest_step_crud、autotest_project_crud、autotest_record_crud、autotest_task_crud、autotest_case_crud、autotest_env_config_crud、autotest_detail_crud、autotest_data_source_crud、autotest_report_crud、autotest_env_crud、department_crud、user_crud |
| ⚪ N/A | audit_crud（无 created_user，系统生成）、autotest_data_generate_crud（空占位文件） |

**本次范围：仅 autotest 模块的 11 个含 created_user 的 crud**（router/role/menu/department/user 等系统数据不在本次范围；record 因 Celery 豁免）。

## 三、已确定的设计决策

| 决策点 | 结论 |
|--------|------|
| is_superuser 来源 | **(a) 上下文增强**：在 ctx 增加 `is_superuser` contextvar（极小共享改动，无额外查询） |
| 批量操作策略 | **逐条校验归属**，任一条越权则**整批失败**（严格） |
| created_user 为空的老数据 | **放行**（兼容历史数据） |
| 接入范围 | **autotest 全部接入**（record 豁免 Celery） |

## 四、实现逻辑

### 第 1 部分：上下文增强（共享代码，2 处极小新增）
- **`backend/services/ctx.py`**：新增 `CTX_IS_SUPERUSER: ContextVar[bool]`（默认 False）+ `get_current_is_superuser()`。
- **`backend/services/dependency.py` 的 `AuthControl.is_authed`**：认证成功后，紧挨现有 `CTX_USERNAME.set(...)` 增加 `CTX_IS_SUPERUSER.set(bool(user.is_superuser))`。
- 影响面：纯新增，不改变现有行为。

### 第 2 部分：核心守卫 `backend/applications/aotutest/services/ownership.py`

**单条守卫 `ensure_owner_or_superuser(record, *, owner_field="created_user")`**，判定顺序：
1. `get_current_is_superuser()` 为真 → 放行（超级用户）。
2. `get_current_username()` 为 None（无 HTTP 上下文，如 Celery）→ 放行（调用方负责）。
3. `record.created_user` 为空/空白 → 放行（老数据兼容）。
4. `record.created_user`（大写）== 当前用户名（大写）→ 放行（本人）。
5. 以上均不满足 → 抛 403（`ForbiddenException`，具体异常类实施时确认）。

**批量守卫 `ensure_owners_or_superuser(records, *, owner_field="created_user")`**：
- 超级用户 / 无上下文 → 整批放行。
- 否则遍历每条：created_user 为空 → 跳过该条；非空且非本人 → 立即抛 403，整批失败。

### 第 3 部分：各 crud 接入
- **单条改/删**：方法内本就 `get_or_error` 取出记录，其后加 `await ensure_owner_or_superuser(record)`。
- **批量改/删**：先按 id 取现有记录，调 `await ensure_owners_or_superuser(existing_records)`。
- **upsert 类**（`batch_update_or_create_*`）：仅对"带 id 的更新项"取现有记录校验；新建项无 created_user，不校验。
- **`autotest_record_crud`**：Celery 触发、无上下文 → 不接入（豁免）。

## 五、行为边界

| 场景 | 结果 |
|------|------|
| 超级用户改/删任何数据 | ✅ 放行 |
| 无 HTTP 上下文（Celery/系统任务） | ✅ 放行（调用方保证） |
| 记录 created_user 为空（老数据） | ✅ 放行 |
| 本人改/删自己创建的数据 | ✅ 放行 |
| 非超级用户改/删他人有主数据 | ❌ 403 拒绝 |
| 批量中混入他人有主记录 | ❌ 整批 403（严格） |
| 批量中的新建记录（无 id） | ✅ 不校验归属 |
| 用户名大小写差异 | ✅ 统一大写后比较，不误拒 |

## 六、用户感知

| 角色/场景 | 用户感知 |
|-----------|----------|
| 超级用户 | 无限制，无感知 |
| 普通用户操作自己的数据 | 正常，无感知 |
| 普通用户改/删他人数据 | 操作失败，前端弹出后端错误提示 |
| 批量保存混入他人数据 | 整次保存失败，提示无权操作 |

- 后端抛 403 + message，前端 axios 拦截器统一弹错误提示（实施时确认拦截器会展示 403 message）。
- **可选 UX 增强**（非必须）：列表接口返回 `created_user`，前端对非超级用户隐藏/禁用他人数据的编辑/删除按钮。当前 `created_user` 在部分 `to_dict` 中被排除，若做此增强需后端返回该字段。

## 九、风险与注意事项

- **保存主链路**（`batch_update_or_create_cases`/`batch_update_or_create_steps`）是高频核心路径，接入须谨慎，充分回归。
- 用户名比较统一大写，注意 `created_user` 长度截断（16 位）。
- 异常类（403）实施时确认现有 `ForbiddenException` 的具体名称与前端拦截器展示。
- 系统管理数据（router/role/menu/department/user）本次**不接入**；如需限制，建议另行评估（通常应仅限超级用户操作，而非"谁创建归谁"）。
